### Project Overview and Architecture
Neverball is a 3D marble-rolling game built in C, utilizing OpenGL for rendering and SDL for input and window management. The codebase is roughly divided into core shared libraries (`share/`), the main Neverball game (`ball/`), and the Neverputt mini-golf spin-off (`putt/`).

The architecture heavily relies on a state machine pattern (defined in `share/state.c`), where discrete screens or gameplay modes are encapsulated in individual source files (e.g., `ball/st_title.c`, `ball/st_play.c`, `ball/st_party.c`). The core gameplay loop processes physics ticks (usually at 100Hz) decoupled from the visual rendering framerate.

### Key Subsystems and Patterns
1. **State Machine (`share/state.c`):** Game flow is managed by pushing and popping states. Each state must provide `enter`, `leave`, `timer` (logic update), and `paint` (rendering) function pointers.
2. **Physics Engine (`share/solid_sim.c` & `ball/game_server.c`):** Handles continuous collision detection using a sweep-and-prune approach against level geometry. The `game_server.c` file is massive and acts as the authoritative source for ball physics, item collection, and mode-specific rules.

### Architectural Patterns & Core Subsystems

**1. State Machine Architecture (`share/state.c`)**
The application flow is driven by a hierarchical state machine. Each distinct screen or gameplay phase (e.g., Main Menu `st_title.c`, Gameplay `st_play.c`, Pause Menu `st_pause.c`, Party Mode Selection `st_party.c`) is a state. States define specific callbacks: `enter()`, `leave()`, `timer()` (for logical ticks), and `paint()` (for rendering). This modularizes the codebase and allows states to be pushed and popped seamlessly (e.g., pausing the game pushes `st_pause` over `st_play`).

**2. Client/Server Decoupling (`ball/game_server.c` & `ball/game_client.c`)**
Despite being a local single-player/local-multiplayer game, Neverball isolates its simulation logic from its rendering layer:
- **Server:** Runs at a fixed tick rate (typically 100Hz). It calculates physics, sweeps collisions against the BSP map geometry, handles item collection, and tracks scores/timers.
- **Client:** Runs at the display's refresh rate. It interpolates between the discrete physics frames provided by the server to ensure smooth rendering, and handles audio cues, visual effects (particle trails), and the HUD.

**3. Networking and Replay System (`share/cmd.c`)**
Input is not fed directly into the physics engine. Instead, player inputs (joystick tilts, jump button presses, item activations) are serialized into "Commands" (`CMD_TILT`, `CMD_JUMP_READY`, etc.). These commands are queued and executed by the server. This design makes the game fully deterministic, enabling the Ghost and Replay system (`ball/demo.c`), where command streams are recorded to `.gho` files and played back seamlessly.

**4. Physics Engine (`share/solid_sim.c`)**
The physics engine employs continuous collision detection (sweep-and-prune) against static BSP geometry (`.sol` files compiled from `.map` files). It handles complex interactions like varying restitution (bounciness), variable gravity zones, and moving platforms.

**5. Custom GUI Framework (`share/gui.c`)**
The game uses an immediate-mode-like GUI layout system mapped to an orthographic projection (`video_push_ortho`). UI elements like labels, buttons, and arrays (`gui_harray`, `gui_varray`) are structured dynamically.

This architecture guarantees determinism, forming the backbone of the Ghost and Replay systems (`ball/demo.c`), where a stream of commands is recorded to a `.gho` file and played back.
